Generics usando a Trait Display em Rust

A Display é uma trait usada para permitir que um valor seja exibido com:

println!("{}", valor);

Quando usamos Generics, o Rust não sabe automaticamente se o tipo genérico T pode ser mostrado com {}. Por isso usamos um Trait Bound com Display.

Exemplo básico
use std::fmt::Display;

fn mostrar<T: Display>(valor: T) {
    println!("{}", valor);
}

fn main() {
    mostrar(10);
    mostrar(3.14);
    mostrar("Rust");
}

Aqui:

T: Display

significa:

T pode ser qualquer tipo, desde que implemente a trait Display.

Então:

T
↓
tipo genérico

Display
↓
comportamento exigido

T: Display
↓
T precisa saber ser exibido com {}
Por que isso é necessário?

Se você fizer:

fn mostrar<T>(valor: T) {
    println!("{}", valor);
}

o compilador reclama.

Porque T poderia ser qualquer tipo, e nem todo tipo implementa Display.

O Rust precisa da garantia:

T: Display

para permitir:

println!("{}", valor);
Usando a sintaxe where

A mesma função pode ser escrita assim:

use std::fmt::Display;

fn mostrar<T>(valor: T)
where
    T: Display,
{
    println!("{}", valor);
}

Isso é equivalente a:

fn mostrar<T: Display>(valor: T)

A forma com where costuma ficar melhor quando existem várias restrições.

Exemplo com dois Generics
use std::fmt::Display;

fn mostrar<T: Display, U: Display>(a: T, b: U) {
    println!("Primeiro: {}", a);
    println!("Segundo: {}", b);
}

fn main() {
    mostrar("Rust", 10);
    mostrar(3.14, "Python");
}

Aqui:

T = primeiro tipo
U = segundo tipo

E ambos precisam implementar:

Display
Com where
use std::fmt::Display;

fn mostrar<T, U>(a: T, b: U)
where
    T: Display,
    U: Display,
{
    println!("{} {}", a, b);
}

Isso facilita quando a função começa a ter vários Generics.

Lifetimes e Dangling Pointers em Rust

Esses dois assuntos estão diretamente ligados.

A ideia principal é:

LIFETIME
→ controla/representa por quanto tempo referências são válidas

DANGLING POINTER
→ referência/ponteiro que aponta para uma região de memória que já não é válida

Rust usa regras de Borrowing + Lifetimes
para impedir referências penduradas em código seguro.
1. O que é um Dangling Pointer?

Imagine:

fn main() {
    let referencia;

    {
        let numero = 10;

        referencia = &numero;
    }

    println!("{}", referencia);
}

Esse código não compila.

O problema está aqui:

{
    let numero = 10;

    referencia = &numero;
}

Dentro do bloco:

numero
  ↓
10

referencia
  ↓
&numero

Mas quando o bloco termina:

{
    let numero = 10;
    referencia = &numero;
}
                    ↓
              numero deixa
              de ser válido

Se Rust permitisse:

println!("{}", referencia);

teríamos conceitualmente:

referencia
    │
    ▼
 memória que não pertence mais
 a um valor válido naquele escopo

    ↓

DANGLING REFERENCE

O Borrow Checker detecta isso durante a compilação e rejeita o programa.

2. O que é Lifetime?

Lifetime significa literalmente:

tempo de vida

Em Rust, lifetimes descrevem a validade das referências.

Exemplo:

fn main() {
    let numero = 10;

    let referencia = &numero;

    println!("{}", referencia);
}

Conceitualmente:

numero
│
├─────────────── lifetime de numero
│
│   referencia
│   ├─────────── lifetime de referencia
│   │
▼   ▼

A referência não pode ser usada além do período em que o dado referenciado permanece válido.

Regra mental:

A REFERÊNCIA
não pode ser válida por mais tempo
do que o dado ao qual ela se refere.
3. Lifetime não significa manter o objeto vivo

Esse detalhe é muito importante.

Lifetime não aumenta o tempo de vida de uma variável.

Isso:

'a

não significa:

Mantenha esse valor na memória durante 'a.

Significa aproximadamente:

Existe uma relação de validade entre essas referências que o compilador precisa verificar.

Lifetimes são principalmente uma forma de expressar relações entre referências.

4. Lifetimes normalmente são inferidos

Você já utiliza lifetimes mesmo sem escrever:

'a

Por exemplo:

fn tamanho(texto: &String) -> usize {
    texto.len()
}

Existe um lifetime associado a:

&String

mas o compilador consegue inferi-lo.
