1. Iniciando API com Rocket

Rocket é um framework web para Rust usado para criar APIs e aplicações web.

No Cargo.toml:

[dependencies]
rocket = { version = "0.5", features = ["json"] }

API básica:

#[macro_use]
extern crate rocket;

#[get("/")]
fn index() -> &'static str {
    "API funcionando!"

#[launch]
fn rocket() -> _ {

Temos:

7. Gerando Token JWT para login

JWT significa:

JSON Web Token

É muito utilizado para autenticação de APIs.

O fluxo básico é:

Usuário
   ↓
POST /login
   ↓
email + senha
   ↓
Servidor valida
   ↓
JWT gerado
   ↓
Token enviado ao cliente

Um JWT normalmente possui:

HEADER
.
PAYLOAD
.
SIGNATURE

Conceitualmente:

xxxxx.yyyyy.zzzzz

Para trabalhar com JWT em Rust, pode-se utilizar uma crate como jsonwebtoken.

[dependencies]
jsonwebtoken = "10"
serde = { version = "1", features = ["derive"] }

Claims:

use serde::{Deserialize, Serialize};

#[derive(Debug, Serialize, Deserialize)]
struct Claims {
    sub: String,
    exp: usize,
}

O sub identifica o sujeito/usuário e exp representa a expiração.

Importante: JWT normalmente é assinado, não criptografado. O payload de um JWT comum não deve ser tratado como secreto.

8. Middleware para validar JWT

Depois do login, o cliente envia o token nas próximas requisições.

Normalmente:

Authorization: Bearer <token>

O servidor precisa verificar esse token antes de liberar uma rota protegida.

No Rocket, uma forma comum de implementar isso é com um Request Guard.

Conceitualmente:

struct UsuarioAutenticado {
    usuario_id: String,
}

Depois uma rota protegida pode exigir esse tipo:

#[get("/perfil")]
fn perfil(
    usuario: UsuarioAutenticado
) -> String {
    format!(
        "Usuário autenticado: {}",
        usuario.usuario_id
    )
}

A ideia é:

Requisição
    ↓
Authorization: Bearer JWT
    ↓
Request Guard
    ↓
Token existe?
    ↓
Assinatura válida?
    ↓
Token expirou?
    ↓
Claims válidas?
    ↓
SIM → libera rota
NÃO → 401 Unauthorized

Iniciando App Web com Rocket

Antes estávamos usando Rocket principalmente como API. Agora podemos usá-lo para servir páginas HTML.

Uma estrutura inicial:

meu_app/
├── Cargo.toml
├── src/
│   └── main.rs
├── templates/
│   └── index.html.tera
└── static/
    ├── css/
    └── js/

Dependências:

[dependencies]
rocket = "0.5"
rocket_dyn_templates = { version = "0.2", features = ["tera"] }

Exemplo:

#[macro_use]
extern crate rocket;

use rocket_dyn_templates::{context, Template};

#[get("/")]
fn index() -> Template {
    Template::render(
        "index",
        context! {
            titulo: "Minha aplicação"
        },
    )
}

#[launch]
fn rocket() -> _ {
    rocket::build()
        .mount("/", routes![index])
        .attach(Template::fairing())
}

Aqui:

GET /
 ↓
index()
 ↓
Template::render()
 ↓
index.html.tera
 ↓
HTML
 ↓
Navegador

o navegador recebe algo equivalente a:

3. Arquitetura com Controllers

Quando o projeto aumenta, colocar todas as rotas no main.rs deixa o código difícil de manter.

Podemos separar:

src/
├── main.rs
├── controllers/
│   ├── mod.rs
│   └── usuario_controller.rs
├── models/
│   ├── mod.rs
│   └── usuario.rs
└── repositories/
    ├── mod.rs
    └── usuario_repository.rs

No:

controllers/mod.rs

podemos declarar:

pub mod usuario_controller;

E em usuario_controller.rs:

use rocket_dyn_templates::{context, Template};

#[get("/usuarios")]
pub fn index() -> Template {
    Template::render(
        "usuarios/index",
        context! {},
    )
}

No main.rs:

mod controllers;

E registramos:

.mount(
    "/",
    routes![
        controllers::usuario_controller::index
    ],
)

A arquitetura fica:

Request
   ↓
Controller
   ↓
Service / Repository
   ↓
Dados
   ↓
Controller
   ↓
Template
   ↓
HTML
4. Application Layout

Um layout evita repetir a mesma estrutura HTML em todas as páginas.

Por exemplo:

<!DOCTYPE html>
<html>
<head>
    <title>{% block title %}Minha aplicação{% endblock %}</title>
</head>

<body>

    <nav>
        <a href="/">Home</a>
        <a href="/usuarios">Usuários</a>
    </nav>

    <main>
        {% block content %}
        {% endblock %}
    </main>

</body>
</html>

Uma página pode estender esse layout:

{% extends "layout" %}

{% block title %}
Usuários
{% endblock %}

{% block content %}

<h1>Usuários</h1>

{% endblock %}

Assim:

layout
├── HTML
├── head
├── navbar
├── main
└── estrutura comum

Página
└── conteúdo específico

Isso reduz repetição.
